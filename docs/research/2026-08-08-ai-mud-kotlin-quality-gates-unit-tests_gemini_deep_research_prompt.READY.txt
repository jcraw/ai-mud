RESEARCH QUESTIONS

1) Quality gates for an AI-maintained Kotlin multi-module game engine
Cover correctness, structure/architecture, tests, docs-as-contracts, security/secrets, performance, release readiness, and process/harness gates.
Map DIGEST-007 ROI gates onto JVM equivalents (compile, detekt/ktlint or alternatives, dependency/module boundaries, API surface, etc.).

2) Strong unit tests WITHOUT coverage theater
What should agents write tests for in a domain-heavy engine (pure core rules, parsers, world graph, combat math, inventory contracts)?
What should NOT be unit-tested (LLM calls, flaky testbot, pure GUI chrome)?
How to prevent weak assertions that only chase coverage %.
Role of property-based tests, characterization/legacy tests for known-red suites, contract tests across modules.
When mutation testing is worth it (which modules) and default score policy.

3) AI-specific failure modes and anti-gaming
Test gaming (editing tests to match broken code), hallucinated APIs, thrashing full-suite green-up, token-bloated test dumps, flaky LLM-dependent tests.
Safeguards: test file locks, N-retry caps, known residual failure lists, touched-scope lanes.

4) Layered verify architecture for AI MUD
Propose default/fast/full lanes suitable for ticket verify: fields (e.g. compile-only vs :core:test vs integration vs full).
How to handle pre-existing reasoning failures without lying about green.
Where testbot/E2E fits (cost, flakiness, optional).

5) 30/60/90 implementation plan for THIS repo
Concrete Gradle tasks, tools, thresholds, file paths, and ticket-shaped backlog.
Minimal viable first week vs later.
